# OneDay

AI-driven text RPG with TUI interface. Highly modular, narrative-focused, everything powered by AI.

---

## Stack

| Component | Technology |
|-----------|------------|
| Language | Go 1.24+ |
| TUI | Bubbletea + Bubbles + Lipgloss |
| Database | SQLite + sqlite-vec (vector search) |
| AI | Claude Code CLI → LiteLLM → OpenRouter (fallback chain) |
| Embeddings | text-embedding-3-small via LiteLLM |
| Plugins | Lua (gopher-lua) — v2+ |

## Architecture Principles

1. **Nothing hardcoded** — stats, skills, NPCs, objectives, locations, items, achievements are all generated by AI at runtime based on the story's rules and context
2. **Modularity first** — every system (combat, crafting, challenge, etc.) is a separate module with clean interfaces
3. **AI proposes, engine decides** — AI suggests narrative and state changes, the game engine validates and applies them. Dice rolls, stat checks, and damage calculations happen in Go code, not in the AI
4. **Chat is always present** — even during combat and crafting, the player can type free actions
5. **Free action always available** — every choice list includes an option for the player to write their own action
6. **Start from nothing** — characters begin with minimal stats, no traits, no skills. Everything is earned through gameplay
7. **Persistent context** — full chat history saved per session, RAG for long-term memory across sessions

## Data Flow

```
[Player Input] → [Context Builder] → [AI Call] → [Response Parser] → [Engine Validation] → [State Update] → [TUI Render]
```

- Context Builder: assembles system prompt + relevant RAG chunks + recent chat + current state
- AI returns structured JSON (narrative, choices, state_changes, challenges, achievements)
- Engine validates state changes, executes dice rolls/checks, updates SQLite
- TUI renders with appropriate styling based on mood/genre

---

## AI Provider Chain

```
config.yaml → provider_priority: [claude-code, litellm, openrouter]
```

- **Claude Code**: shell out to `claude -p "prompt" --output-format json`
- **LiteLLM**: OpenAI-compatible API at configured endpoint
- **OpenRouter**: direct API with model routing
- Automatic fallback: if provider 1 fails/timeouts → try provider 2 → etc.


## Conventions

- **Go style**: standard `gofmt`, no external linters beyond `go vet`
- **Error handling**: wrap errors with `fmt.Errorf("context: %w", err)`
- **Interfaces**: define at consumer side, keep small (1-3 methods)
- **Naming**: `internal/engine/combat.go` not `internal/engine/combat/combat.go` — flat within packages
- **JSON**: use `encoding/json` with struct tags, `omitempty` where appropriate
- **Tests**: table-driven, `_test.go` in same package
- **Commits**: conventional commits `type(scope): description`
- **No npm**: use `bun` if any JS tooling needed (unlikely)

## GSD (Get Shit Done) Workflow

This project uses GSD for structured AI-assisted development. Config: `.planning/config.json`

### Common Commands

| Command | When to use |
|---------|-------------|
| `/gsd-quick` | Small, well-scoped tasks (single file, quick fix) |
| `/gsd-discuss-phase` | Before planning — gather context and requirements for a phase |
| `/gsd-plan-phase` | Create detailed task plan for a roadmap phase |
| `/gsd-execute-phase` | Execute planned tasks with wave parallelization |
| `/gsd-verify-work` | Validate completed work through UAT |
| `/gsd-ship` | Create PR, review, prepare for merge |
| `/gsd-fast` | Trivial inline task — no subagents |
| `/gsd-progress` | Check where we are and what's next |
| `/gsd-debug` | Systematic debugging with persistent state |
| `/gsd-code-review` | Review changed files for bugs and quality |

### Workflow

For major roadmap phases (v0.1, v0.2, etc.):
1. `/gsd-discuss-phase` — clarify requirements
2. `/gsd-plan-phase` — create atomic task plan
3. `/gsd-execute-phase` — execute in parallel waves (fresh context per agent)
4. `/gsd-verify-work` — UAT validation
5. `/gsd-ship` — commit and close

For quick tasks: `/gsd-quick` or `/gsd-fast`

### Config

- **Model profile**: `balanced` (Opus for planning, Sonnet for execution)
- **Branching**: `phase-based` (branch per phase)
- **Worktrees**: enabled (isolated execution agents)
- **Nyquist validation**: disabled (no automated tests yet)
- **UI phase**: disabled (TUI project, not web frontend)
