# Plan 5.2: Chapter System, Separate Chat Sessions, and /narrator Command

## Objective

Implement three interconnected features:
1. **Chapter system (STOR-05)**: AI determines chapter boundaries, generates chapter summaries, chapters are tracked and viewable.
2. **Separate chat sessions (STOR-04)**: Combat, crafting, and deep NPC dialogue get their own JSONL files and DB message types, separate from the main narrative chat.
3. **/narrator command (CMD-03, CMD-04)**: Player can speak to the AI as a game master for meta-level world-building, lore injection, NPC depth, and narrative steering. Changes auto-update story.json, NPC data, and world state.

## Key Decisions

- **Chapter detection**: The AI's response already has access to the narrative flow. Add a `chapter_end` field to the AI response format. When the AI sets `chapter_end: true`, the engine closes the current chapter, generates a summary (via RAG summarizer reuse), and starts a new one.
- **Separate sessions**: Use `message_type` field (already in ChatMessage model) to tag messages as "narrative", "combat", "crafting", "dialogue". Separate JSONL files written alongside main.jsonl. The DB already supports this via the message_type column.
- **/narrator flow**: Narrator input is processed by a separate AI call with a different system prompt (NarratorMeta prompt). The AI responds with acknowledgment + structured state changes. The response is shown to the player but not inserted into the narrative flow.
- **/narrator state changes**: Reuse the existing `ApplyStateChanges` engine with extended change types for story setting updates, world state updates, and NPC modifications.

## Verification

- [ ] AI can signal chapter end; engine creates chapter record with AI-generated summary
- [ ] /journal command shows chapter list with titles and summaries
- [ ] Separate JSONL files created for combat/crafting/dialogue sessions
- [ ] Chat messages tagged with correct message_type in DB
- [ ] /narrator (/n) command works — player can inject lore, steer narrative, modify NPCs
- [ ] /narrator changes persist to story setting, NPC data, and world state
- [ ] /narrator interactions are logged but don't increment turn counter
- [ ] Existing gameplay not broken — chapter detection is passive, /n is opt-in

// ChapterManager handles chapter lifecycle (creation, transitions, summaries).
type ChapterManager struct {
    db      *storage.DB
    storyID string
    rag     *rag.RAG  // for generating chapter summaries (optional)
    router  AIProvider

func NewChapterManager(db *storage.DB, storyID string, rag *rag.RAG, router AIProvider) *ChapterManager

// EnsureCurrentChapter creates chapter 1 if none exists.
func (cm *ChapterManager) EnsureCurrentChapter(startTurn int) error

// HandleChapterEnd closes current chapter with a summary and opens the next one.
// Called when AI response contains chapter_end: true.
func (cm *ChapterManager) HandleChapterEnd(ctx context.Context, currentTurn int, chapterTitle string) error

// GetChapterSummaries returns all chapter summaries as formatted text (for /journal).

**HandleChapterEnd flow:**
1. Get current chapter from DB
2. Fetch messages from `start_turn` to `currentTurn` for the chapter
3. Generate chapter summary via AI (reuse summarizer prompt or dedicated chapter summary prompt)
4. Embed the chapter summary and store in RAG vector store with chunk_type "chapter"
5. Update chapter record with end_turn and summary
6. Create new chapter record (chapter_number + 1, start_turn = currentTurn + 1)
7. Update world_state.current_chapter

```go
package engine

// NarratorCommand processes /narrator meta-commands.
// These are out-of-story interactions where the player speaks to the AI as game master.
type NarratorCommand struct {
    router    *ai.Router
    db        *storage.DB
    story     *storage.Story
    character *storage.Character
    world     *storage.WorldState
    rag       *rag.RAG
}

// NarratorResponse is the AI's response to a /narrator command.
type NarratorResponse struct {
    Message      string                 `json:"message"`       // shown to player
    StateChanges map[string]interface{} `json:"state_changes"` // applied to game state
}

func NewNarratorCommand(router *ai.Router, db *storage.DB, story *storage.Story, char *storage.Character, world *storage.WorldState, rag *rag.RAG) *NarratorCommand

// Execute processes a narrator command and returns the response.
// The input is the player's text after "/n " or "/narrator ".
func (nc *NarratorCommand) Execute(ctx context.Context, input string) (*NarratorResponse, error)
```

**Execute flow:**
1. Build a narrator-meta system prompt (different from the gameplay narrator prompt)
2. Include current story setting, world state, NPC list for context
3. Send the player's /n input to the AI
4. Parse the response (JSON: message + state_changes)
5. Apply state changes using extended ApplyStateChanges:
   - `setting_factions_add`: append to story.json factions
   - `setting_cultures_add`: append to story.json cultures
   - `setting_dangers_add`: append to story.json dangers
   - `setting_rules_add`: append to story.json rules
   - `npc_thoughts`, `npc_desires`, `npc_notes`: update NPC data
   - `world_location_add`: add to known locations
   - `world_event_add`: add to global events
   - `world_faction_standing`: update faction standings
   - Standard state_changes (npc_disposition, etc.) also supported
6. Return the message to display to the player
7. Log the interaction in chat DB with message_type "narrator" (does NOT increment turn counter)

## Wave Structure

**Wave 1** (Tasks 1, 4, 7): Storage layer + prompts — independent foundation pieces. No cross-dependencies.

**Wave 2** (Tasks 2, 5): Chapter engine + /narrator command. Task 2 depends on Task 1. Task 5 depends on Task 1 (for state changes) but can be developed in parallel.

**Wave 3** (Tasks 3, 6): Integration — wire chapter management into narrator, extend state applicator for /narrator changes. Both depend on Wave 2.

## Notes

- The /narrator command is the most complex feature. The AI needs a good prompt to understand that it's operating at a meta level, not in-story. The NarratorMeta prompt must clearly separate "narrator voice" from "story voice".
- Chapter detection is intentionally AI-driven, not rule-based. The AI decides when a chapter ends based on narrative flow. This keeps it organic and story-appropriate.
- Separate JSONL files for sub-sessions (Task 4) prepare the infrastructure for Phase 6 (combat and crafting), which will actually use them. In this phase, we just build the plumbing.
- /narrator state changes use the same `ApplyStateChanges` pipeline as regular gameplay, just with additional change types. This keeps the engine consistent.
