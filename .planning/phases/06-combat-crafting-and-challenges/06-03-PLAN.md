# Plan 6.3: Challenge TUI + Narrative Integration

## Objective

Build the visual components for challenge resolution (animated dice roll, RPS display, memory sequence, quick-time events, riddle input) and wire the entire challenge system into the narrative flow. When the AI includes a challenge in its response, the engine detects it, the TUI displays the appropriate challenge UI, the engine resolves the outcome, and the AI then narrates the result.

## Key Decisions

- **Challenges are inline overlays**, not separate views. Unlike combat (which is a full-screen mode), challenges are brief interruptions displayed as overlays on top of the narrative view. The player resolves them and returns to the narrative immediately.
- **Dice animation**: A Bubbletea component that rapidly cycles through numbers for 1-2 seconds before landing on the actual result. Pure visual flair — the result is pre-computed by the engine.
- **Two-phase challenge flow**: (1) AI includes challenge spec in response, TUI shows the challenge overlay, player interacts. (2) Engine resolves pass/fail. (3) TUI sends result back to AI for narrative continuation.
- **Passive vs active challenges**: Stat checks and item/skill/relationship checks are passive — resolved instantly by the engine with a brief notification. Dice rolls and mini-games are active — they require TUI display and player interaction.
- **Challenge results feed back to AI**: After resolution, the narrator sends a follow-up message like `"[Challenge Result: dice_roll PASSED (roll: 72, total: 82, difficulty: 60)]"` so the AI can narrate appropriately.

## Verification

- [ ] Dice roll shows animated d100 cycling for ~1.5s before revealing result

- [ ] RPS shows player choice, AI choice, and outcome with brief animation
- [ ] Memory sequence shows symbols one by one, then prompts player to repeat

package components

import (
    "fmt"
    "math/rand"
    "time"

    tea "github.com/charmbracelet/bubbletea"
    "github.com/charmbracelet/lipgloss"

    "github.com/crimsab/oneday/internal/tui/theme"
)

// DiceResultMsg is emitted when the dice animation finishes.
type DiceResultMsg struct {
    Passed bool
}

// diceTickMsg advances the dice animation frame.
type diceTickMsg struct{}

// DiceModel renders an animated d100 dice roll with modifiers and result.
type DiceModel struct {
    // Configuration (set once)
    FinalRoll   int         // the actual d100 result (pre-computed by engine)
    Total       int         // roll + sum(modifiers)
    Difficulty  int         // threshold to pass
    Modifiers   []ModDisplay // source + value for each modifier
    Passed      bool        // final outcome

    // Animation state
    displayedNumber int    // currently shown number (cycles rapidly)
    frame           int    // animation frame counter
    maxFrames       int    // total frames (~30 at 20fps = 1.5s)
    done            bool   // animation complete
    active          bool   // animation running
    tickInterval    time.Duration
}

// ModDisplay is a modifier shown in the dice overlay.
type ModDisplay struct {
    Source string
    Value  int
}

// NewDiceModel creates a dice roll animation.
// All values are pre-computed by the engine — this is purely visual.
func NewDiceModel(roll, total, difficulty int, modifiers []ModDisplay, passed bool) DiceModel

// Start begins the dice animation. Returns the first tick cmd.
func (d *DiceModel) Start() tea.Cmd

// Update handles animation ticks.
func (d DiceModel) Update(msg tea.Msg) (DiceModel, tea.Cmd)

// View renders the dice animation.
func (d DiceModel) View() string
```

**Animation logic:**
1. `maxFrames = 30`, `tickInterval = 50ms` → ~1.5 second animation
2. Each tick: `displayedNumber = rand.Intn(100) + 1` (random cycling)
3. Last 5 frames: slow down (tick every 100ms) for dramatic effect
4. Final frame: show actual `FinalRoll`
5. After animation: show full breakdown and emit `DiceResultMsg`

**View rendering:**
```
┌──────────────────────────────┐
│        🎲 DICE ROLL          │
│                              │
│          [ 73 ]              │  ← large, animated number
│                              │
│   Roll:        73            │
│   + Stealth:   +8            │  ← each modifier
│   + Lucky Ring: +5           │
│   ─────────────────          │
│   Total:       86            │
│   Difficulty:  60            │
│                              │
│       ✓ PASSED!              │  ← green if pass, red if fail
│                              │
│   Press any key to continue  │
└──────────────────────────────┘
```

The large number uses `lipgloss.NewStyle().Bold(true).Foreground(theme.Highlight)` and is centered.
During animation, it flickers through random values.
After resolution: green `PASSED` or red `FAILED`.

package views

import (
    tea "github.com/charmbracelet/bubbletea"

    "github.com/crimsab/oneday/internal/engine"
    "github.com/crimsab/oneday/internal/tui/components"
)

// ChallengeResolvedMsg carries the result of a challenge back to the narrative.
type ChallengeResolvedMsg struct {
    Spec   *engine.ChallengeSpec
    Result *engine.ChallengeResult
}

// ChallengeView manages the appropriate challenge component based on type.
// It acts as a dispatcher — wrapping dice, RPS, memory, quicktime, or riddle models.
type ChallengeView struct {
    spec   *engine.ChallengeSpec
    result *engine.ChallengeResult

    // Only one of these is active at a time
    dice      *components.DiceModel
    rps       *components.RPSModel
    memory    *components.MemoryModel
    quicktime *components.QuickTimeModel
    riddle    *components.RiddleModel

    // For passive challenges (stat/item/skill/relationship checks)
    passive       bool
    passiveResult *engine.ChallengeResult

    active bool
    width  int
    height int
}

// NewChallengeView creates the appropriate challenge UI for a spec.
// challengeEngine is used to resolve passive challenges immediately.
// For active challenges, it sets up the appropriate interactive component.
func NewChallengeView(
    spec *engine.ChallengeSpec,
    ce *engine.ChallengeEngine,
    char *storage.Character,
    db *storage.DB,
    storyID string,
    width, height int,
) (*ChallengeView, tea.Cmd)

// Update handles messages for the active challenge component.
func (cv *ChallengeView) Update(msg tea.Msg) (*ChallengeView, tea.Cmd)

// View renders the active challenge component.
func (cv *ChallengeView) View() string

// IsPassive returns true if this was a passive challenge (already resolved).
func (cv *ChallengeView) IsPassive() bool
```

**NewChallengeView logic:**
1. Parse `spec.Type`:
   - `stat_check`, `item_check`, `skill_check`, `relationship_check`:
     - Resolve immediately via `ce.Resolve(spec, char, db, storyID)`
     - Set `passive = true`, store result
     - Return a cmd that emits `ChallengeResolvedMsg` after a brief 1.5s notification
   - `dice_roll`:
     - Resolve via `ce.Resolve()` to get the actual result (pre-compute)
     - Create `DiceModel` with the pre-computed values
     - Return dice start cmd
   - `mini_game`:
     - Based on `spec.MiniGame`:
       - `"rps"` → create `RPSModel`
       - `"memory"` → create `MemoryModel` from `spec.Sequence`
       - `"quicktime"` → create `QuickTimeModel` from `spec.TimeLimit`
       - `"riddle"` → create `RiddleModel` from `spec.Riddle`, `spec.Answer`

2. **Update** delegates to the active component and catches result messages:
   - `DiceResultMsg` → build `ChallengeResult`, emit `ChallengeResolvedMsg`
   - `RPSResultMsg` → build `ChallengeResult`, emit `ChallengeResolvedMsg`
   - `MemoryResultMsg` → emit `ChallengeResolvedMsg`
   - `QuickTimeResultMsg` → emit `ChallengeResolvedMsg`
   - `RiddleResultMsg` → emit `ChallengeResolvedMsg`
</action>

- Passive challenges resolve immediately and emit result
- Active challenges launch appropriate interactive component
- All result messages are caught and converted to ChallengeResolvedMsg

## Wave Structure

**Wave 1** (Tasks 1, 2, 3, 4, 8): All challenge components + theme styles. These are independent Bubbletea components with no cross-dependencies. Can be built in parallel.

**Wave 2** (Tasks 5, 7): Challenge view coordinator + narrator prompt update. Task 5 depends on Tasks 1-4 (uses all components). Task 7 is independent (prompt changes only).

**Wave 3** (Task 6): Narrative integration. Depends on Task 5 (ChallengeView) and Task 7 (AI knows about challenges). This is the final wiring that makes everything work end-to-end.

## Notes

- Challenges are brief interruptions, not modes. The player resolves a challenge in seconds and returns to the narrative. This keeps the flow snappy.
- The two-phase approach (AI proposes → engine resolves → AI narrates) ensures the AI can create contextually appropriate challenges while the engine maintains fairness. The AI never knows the dice result in advance.
- Passive challenges (stat checks, item checks) are resolved silently with a brief notification. This avoids breaking flow for routine checks. Only dice rolls and mini-games get full visual treatment.
- The `ChallengeView` coordinator pattern keeps the narrative view clean. It handles all dispatch logic so the narrative view only needs to know about `ChallengeResolvedMsg`.
- Memory sequences use arrow keys for simplicity. This maps well to terminal input and is intuitive ("repeat the pattern"). Sequence length of 4-6 is reasonable for a casual game.
- Quick-time events use a generous default (3 seconds). The AI can adjust this in the spec for harder challenges.
- Riddle answers use fuzzy matching (case-insensitive, trimmed). The AI is instructed to provide single-word or short-phrase answers to minimize false negatives.
- The challenge system is designed to be unobtrusive. If the AI never includes challenges, the game works perfectly fine as pure narrative. Challenges are an enhancement, not a requirement.
